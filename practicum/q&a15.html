			class Solution {
				public boolean isIsomorphic(String s, String t) {
					int[] indexS = new int[200];
					int[] indexT = new int[200];
					int len = s.length();

					if(len != t.length()) {
						return false;
					}

					for(int i = 0; i < len; i++) {
						if(indexS[s.charAt(i)] != indexT[t.charAt(i)]) {
							return false;
						}
						indexS[s.charAt(i)] = i + 1;
						indexT[t.charAt(i)] = i + 1;
					}
					return true;
				}
			}

			class Solution {
				public int numSquares(int n) {
					int[] dp = new int[n + 1];
					dp[0] = 0;
					for (int i = 1; i <= n; i++) {
						int min = i;
						for (int j = 1; j * j <= i; j++) {
							min = Math.min(min, dp[i - j * j] + 1);
						}
						dp[i] = min;
					}
					return dp[n];
				}
			}

Мы наконец-то дошли до автоматизации запросов к базе и познакомились с Hibernate. ORM забирает у программиста часть ответственности за запросы к базе. Это уменьшает количество ошибок и позволяет менять СХД в случае необходимости.

Также, вы рассмотрели паттерн DTO — отделяет сущности ORM и интерфейс сервиса, потому что в общем случае это разные вещи.

Когда вы пишете приложение, может показаться логичным возвращать ровно то, что лежит в БД — то есть Entity.

Но это ошибка — в современном гибком мире вы точно будете менять и БД и интерфейс сервиса, тогда почувствуете боль. Лучше сразу уменьшить связность и отделить интерфейс сервиса от сущности.

Для маппинга есть удобные фреймворки, например mapstruct — вы пишете интерфейс маппера что-куда замапить, а фреймворк генерирует качественный код с проверками.

Еще про транзакции — бывает, что при работе двух человек с БД один делает в ней изменения, а второй их не видит — это чаще всего связано с настройками клиента, выключен автокоммит. Несколько раз сталкивался с этим.

ACID

  • Atomicity — атомарность
  • Consistency — согласованность
  • Isolation — изоляция
  • Durability — устойчивость
Акроним — набор требований к транзакционной системе, обеспечивающий надежную и предсказуемую работу.

Бывает на собеседованиях.

Давайте вместе вспомним, кто расскажет?

A — all or nothing, комплексная транзакция либо выполняется полностью либо никак. Важно — система должна гарантировать атомарность в любых ситуациях — при сетевых проблемах, ошибках программы, отказе железа и тп

C — корректно написанная транзакция сохраняет согласованность данных в БД. То есть все правила и ограничения данных в таблице будут сохранены.

I — параллельные транзакции не должны влиять друг на друга.

D — если транзакция завершилась и пользователю было возвращено ОК, то любые проблемы системы не могут на нее повлиять. Обычно значит, что результат записан в отказоустойчивой СХД.

Проблема N+1

“The Hibernate recommendation is to statically mark all associations lazy and to use dynamic fetching strategies for eagerness. This is unfortunately at odds with the JPA specification which defines that all one-to-one and many-to-one associations should be eagerly fetched by default. Hibernate, as a JPA provider, honors that default. ”
Проблема N + 1 не специфична для JPA и Hibernate, с ней вы можете столкнуться и при использовании других технологий доступа к данным.

Проблема N + 1 возникает, когда фреймворк доступа к данным выполняет N дополнительных SQL-запросов для получения тех же данных, которые можно получить при выполнении одного SQL-запроса.

N запросов в общем случае тяжелее для БД, чем один. Также, гораздо большей проблемой является сетевая задержка — N запросов будут накапливать ее, ведь каждый запрос это общение данных по сети.

Вам рекомендовали в теории все типы связей помечать LAZY, в Hibernate раньше было именно так, но JPA считает по другому — ManyToOne и OneToOne там EAGER по видимому потому что считается, что выгрузка одной сущности мало влияет на производительность. В Hibernate сделали также, но в документации прописана рекомендация LAZY.

Double brace initialisation
Можно рассматривать как синтаксический "сахар" — замена литералам создания списков и ассоциативных массивов.

Это не специальный синтаксис! Создается анонимный класс — внешние скобки, а внутренние — блок инициализации, где он наполняется элементами.

Можно нагенерировать кучу классов — ненужная нагрузка на heap и classloader. Это происходит при каждом инстанциировании!

Проблема всех анонимных классов — они содержат ссылку на сущность, в которой они содержатся.Если в методе вернуть объект анонимного класса, то он потащит за собой ссылку на окружение — сборщик мусора может не оптимально произвести чистку или вообще не очистить внешний класс.

Это может привести к утечке памяти, если этот внешний объект тяжелый. Если с умом использовать — не страшно, но на мой взгляд лучше избегать, потому что минусов больше.

На собесах иногда появляется, проверяют кругозор.
