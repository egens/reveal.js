						class Solution {
							public int splitNum(int num) {
								String number = String.valueOf(num);
								char[] digits = number.toCharArray();
								Arrays.sort(digits);
								int i = digits.length - 1;
								int sum = 0;
								int d = 1;
								while (i >= 0) {
									sum += Character.getNumericValue(digits[i--]) * d;
									if (i < 0) return sum;
									sum += Character.getNumericValue(digits[i--]) * d;
									d *= 10;
								}
								return sum;
							}
						}

CAP

  • Consistency
  • Availability
  • Partition tolerance

CAP теорема — основное ограничение распределенных систем хранения данных.

Его важно знать, потому что в современном мире облаков и микросервисов распределенное хранение является стандартом.

Например, очень популярный ELK стек работает с распределенным хранилищем.

Что такое РСХД — на картинке клиент и два сервера РСХД, которые хранят некоторое значение.

Я уверен, что каждый разработчик будет работать с той или иной распределенной системой хранения.

CAP теорема говорит о том, что РСХД может обеспечить только два из трех свойств.

Дальше поговорим про них подробнее.

Согласованность данных

Записали X — при чтении гарантируется X.
Чтение с любого узла гарантирует результат последней операции записи в любой узел.

На картинке показано, как этого можно добиться.

При отправке клиентом записи v1 на G1, узел G1 отправляет ее также на G2. И только после подтверждения записи от G2 отправляет подтверждение записи клиенту. После подтверждения записи для клиента в СХД на всех узлах она гарантированно сохранилась.
  • Доступность — запрос к работающему серверу гарантирует ответ.
  • Устойчивость к разделению — гарантируется работа при отсутствии связи узлов.


Доказательство CAP
Устойчивость к разделению — на левой картинке сетевая связность нарушена, но система продолжает работать.

На картинке доказательство от противного.

Предположим, что система одновременно обеспечивает согласованность, доступность и устойчивость.

Так как система устойчива, нарушим связность между узлами.

Отправим запрос на изменение данных на первый сервер.

Система доступна — обязана изменить значение. Это показано

Теперь отправим запросы на чтение на оба сервера (в самое правое состояние).

Система доступна — обязана вернуть разные результаты.

Получили противоречие — ведь система по предположению обеспечивает согласованность.

CAP

  • Consistency
  • Availability
  • Partition tolerance
— Choose two wisely
Теперь, что это значит на практике.

На самом деле, если система распределенная, то нельзя гарантировать сетевую связность между узлами.

То есть остается выбор между двумя свойствами.

При сетевой ошибке нужно решить — вернуть пользователю ошибку и уменьшить доступность системы.

Или вернуть имеющийся результат и пожертвовать согласованностью.

Оба свойства согласованности и доступности может обеспечить только СХД без партиций.

Часто останавливаются на доступности, поэтому иногда при обновлении веб-страницы можно видеть, как число лайков может "прыгать".

DAL — DAO

  • Data Access Layer
  • Data Access Object

DAL — абстрактный слой, который уменьшает связность в приложении. Бизнес логика меньше зависит от особенностей системы хранения.

DAO — элементы этого слоя, предоставляющие доступ к различным значениям в СХД.

Если его не делать, то при написании бизнес логики можно привязаться к конкретным фичам БД и при ее изменении придется все переписывать.

В настоящее время, как мне кажется, строгость этого паттерна немного ослабла и этот слой начал размываться в некоторых фреймворках, в том числе в Spring Data.

Это связано с тем, что на практике, БД на проектах меняются не так часто.

Но в некоторых проектах можно встретить и чистую реализацию этого слоя.

В этом спринте вы нарабатываете практику общения с БД.

Обратите внимание, что несмотря на красивую картинку у DAO паттерна есть очевидные минусы.

Например, закрыв абстракцией строку в SQL таблице и написав SELECT операцию по ID, разработчик для получения списка объектов будет делать несколько запросов к БД.

Хотя БД позволяет выполнить операцию получения списка объектов за один запрос.

Эти проблемы и пробует решить Spring Data и Java Persistence API — это реализация DAL слоя.

Наблюдатель (observer)

Хочу сегодня вам также рассказать об одном из самых популярных поведенческих паттернов проектирования Наблюдатель.

Он применяется, когда есть набор классов наблюдателей, в которых нужно запускать некоторые процессы при изменениях в другом Наблюдаемом объекте. Позволяет добиться связи классов один ко многим с низким зацеплением между классами.

Реализация заключается в использовании двух интерфейсов. Subject — его будет имплементировать основной объект, при изменениях в котором нужно запускать действия на ряде других классов. Эти классы должны имплементировать интерфейс Observer. Они будут "наблюдателями" за основным объектом.

Subject имеет три метода — добавление и удаление наблюдателей, а также оповещение их об изменении. Observer имеет метод обработки изменений в наблюдаемом объекте.

ОБЪЯСНИТЬ ПО КАРТИНКЕ КАК ЭТО РАБОТАЕТ

В коде сами методы и поля объектов, а также интерфейсы могут называться иначе. Но если вы встречаетесь с подобной структурой классов, то будете знать, что тут происходит.

Тут стоит отметить, что простые реализации Observer Observable в java.util переведены в статус Deprecated. Потому что накладывают очень существенные ограничения — Observable нельзя сериализовать, они непотокобезопасны и как выражаются разработчики java "не предоставляют достаточно богатые возможность обработки ивент модели".

Вместо них рекомендуется использовать PropertyChangeEvent и PropertyChangeListener из пакета java.beans.
