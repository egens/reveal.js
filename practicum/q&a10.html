Системы сборки

  • Maven, Gradle, Ant
  • Жизненный цикл и фазы
  • Типы репозиториев
  • Parent POM и BOM
  • Многомодульные проекты, Checkstyle
Вы познакомились с системой сборки Maven. Maven и Gradle покрывают подавляющее большинство Java-проектов. Ant — история: появился в 2000 году, управления зависимостями из коробки у него нет, сейчас встречается только в легаси.
Здесь и далее в курсе мы используем Maven. Я лично использую Gradle — у меня патологическая неприязнь к XML. У Gradle описание сборки — код на Groovy или Kotlin DSL, есть инкрементальная сборка и кэш, поэтому на больших проектах он быстрее.
С системой сборки разработчик плотно работает при первоначальной настройке проекта, а дальше изменения вносятся гораздо реже — по мере необходимости.

Жизненный цикл: validate, compile, test, package, verify, install, deploy. Запуск фазы выполняет и все предыдущие. mvn package соберёт jar и прогонит тесты, mvn install ещё и положит артефакт в локальный репозиторий. Перед пушем удобно запускать mvn clean verify — это примерно то, что делает CI.
Полезная команда — mvn dependency:tree: показывает, откуда пришла транзитивная зависимость, когда ловите конфликт версий.
Помните про scope зависимостей: compile по умолчанию, test — только для тестов (JUnit), provided — нужна при компиляции, но не попадает в итоговый артефакт. Lombok подключают именно с provided.

Какие типы репозиториев? Локальный — ~/.m2/repository, удалённый, и центральный — Maven Central, это частный случай удалённого.
В компаниях почти всегда работают через внутренний удалённый репозиторий — Nexus или Artifactory. Он проксирует Central, кэширует артефакты, позволяет проверять их на уязвимости и хранить собственные библиотеки компании. Подключается через mirror в settings.xml.

Наследование POM: spring-boot-starter-parent — родительский POM, от него вы получаете настройки плагинов и версии зависимостей. Поэтому в pom.xml вы пишете стартеры без version.
Сами версии лежат в BOM — spring-boot-dependencies, это POM, в котором есть только dependencyManagement. Если родитель уже занят, BOM можно подключить через dependencyManagement с type pom и scope import. BOM гарантирует, что версии библиотек совместимы друг с другом.

Многомодульный проект — родительский POM с packaging pom и списком modules. Так делят код на api, сервис, общие модели. В курсе многомодульный проект ещё встретится.

Checkstyle — плагин, который проверяет стиль кода по набору правил и может ронять сборку. Если он подключён в pom или в GitHub Actions, прогоняйте его локально — mvn checkstyle:check, иначе будете ловить замечания уже на автопроверке.

Логирование

  • SLF4J — фасад, Logback и Log4j2 — реализации
  • Уровни: TRACE, DEBUG, INFO, WARN, ERROR
  • log.info("Добавлен фильм {}", film)
  • Хранилища логов: ELK (Elasticsearch, Logstash, Kibana), OpenSearch, Grafana Loki
  • Метрики: Prometheus + Grafana
Вы научились писать логи правильным способом. SLF4J — это не сам фреймворк логирования, а фасад, то есть API. Реальную запись делает реализация: в Spring Boot по умолчанию это Logback, он приходит вместе со spring-boot-starter-logging.
Зачем фасад? Код библиотек и ваш код зависят только от SLF4J, а реализацию можно поменять, не трогая код. Это пригодилось в декабре 2021, когда нашли уязвимость Log4Shell в Log4j2 — проектам на фасаде было проще мигрировать.

Уровни: ERROR — что-то сломалось, нужна реакция; WARN — подозрительно, но работаем дальше; INFO — значимые бизнес-события, например «создан пользователь»; DEBUG — детали для отладки; TRACE — совсем подробно. В Spring Boot по умолчанию INFO, уровень для пакета меняется в application.properties: logging.level.ru.yandex.practicum=DEBUG.

Используйте плейсхолдеры {} вместо конкатенации: если уровень выключен, строка не собирается. Исключение передавайте последним аргументом — тогда в лог попадёт стектрейс: log.error("Не удалось обновить фильм {}", id, e).
Не логируйте пароли, токены и персональные данные. В банке за это прилетает от безопасности.

Вкратце покажу, что с логами происходит дальше.
Сервисы пишут в консоль, сборщик (Filebeat, Fluent Bit, Logstash) отправляет их в хранилище. Часто логи пишут сразу в JSON, чтобы по полям было удобно искать.
Обычно хранилище — ELK или OpenSearch, в стеке Grafana — Loki. Там есть полнотекстовый поиск, фильтры и дашборды.
Prometheus + Grafana — это про метрики, а не логи: загрузка CPU, число запросов, время ответа. Логи отвечают на вопрос «что случилось», метрики — «как часто и насколько плохо».
Чтобы найти все логи одного запроса в разных сервисах, в каждую запись добавляют traceId — через MDC в SLF4J.

Логов много, поэтому время хранения обычно ограничено неделей-месяцем.
Если какую-то информацию нужно хранить дольше — например, для аудита, — её сохраняют программно в БД.
У нас даже есть отдельное API для фронта, куда он шлёт свои ошибки, чтобы они тоже логировались централизованно.

Аннотации

  • Метаданные для кода
  • @Override, @Deprecated, @SuppressWarnings, @FunctionalInterface
  • Мета-аннотации: @Retention, @Target
  • Рефлексия
Аннотации — метаданные, которые добавляют к коду. Сами по себе они ничего не делают: их читает и обрабатывает компилятор, annotation processor или фреймворк во время выполнения.

Встроенные аннотации:
@Override — метод переопределяет метод суперкласса или реализует метод интерфейса. Если сигнатура не совпала, компилятор выдаст ошибку. Ставьте всегда — это бесплатная проверка;
@Deprecated — элемент устарел и может быть удалён в будущих версиях, начиная с Java 9 есть параметры since и forRemoval;
@SuppressWarnings — подавляет предупреждения компилятора, например "unchecked";
@FunctionalInterface — компилятор проверит, что в интерфейсе ровно один абстрактный метод.

Мета-аннотации — аннотации над аннотациями.
@Retention определяет, где аннотация живёт: SOURCE — только в исходниках (@Override, аннотации Lombok), CLASS — в байткоде (значение по умолчанию), RUNTIME — доступна через рефлексию. Аннотации Spring и JUnit — RUNTIME. Частая ошибка при написании своей аннотации — забыть RUNTIME, и рефлексия её не видит.
@Target ограничивает, куда можно поставить аннотацию: на класс, метод, поле, параметр.
Элементы аннотации объявляются как методы без параметров, могут иметь default. Допустимые типы: примитивы, String, Class, enum, другие аннотации и массивы из них. Элемент с именем value можно указывать без имени.

Аннотации используются для конфигурации фреймворков (Spring, Hibernate), тестов (JUnit), валидации данных и маппинга в ORM. Они убирают шаблонный код.

Рефлексия — механизм, позволяющий программе во время выполнения исследовать классы, читать и менять значения полей и вызывать методы, в том числе приватные. Менять саму структуру класса — добавлять поля или методы — рефлексия не умеет.
В Java для этого есть Reflection API: Class, Field, Method, Constructor.
Цена рефлексии: она медленнее прямого вызова, ошибки вылезают только в рантайме, а setAccessible ломает инкапсуляцию. С модулями Java 9+ доступ к чужим приватным полям ещё и ограничен.

Использовать готовые аннотации Spring, JUnit и Lombok — нормальная ежедневная работа.
А вот писать свои аннотации с обработкой через рефлексию — инструмент для фреймворков. Внутри Spring полно рефлексии.
Вам рассказали об этом не для того, чтобы вы начали писать свои, а чтобы Spring не казался магией.
В прикладном коде лучше десять раз подумать, прежде чем писать свою аннотацию с рефлексией.

Spring Boot

  • Надстройка над Spring Framework
  • Стартеры, автоконфигурация, встроенный Tomcat
  • Inversion of control (IoC)
  • Dependency injection (DI)
Spring Framework — это IoC-контейнер и набор модулей: web, data, security и т.д. Spring Boot — надстройка над ним, которая убирает ручную настройку.
Стартеры — наборы согласованных зависимостей: spring-boot-starter-web тянет Spring MVC, Jackson и Tomcat.
Автоконфигурация — Boot смотрит, какие классы есть в classpath, и создаёт нужные бины сам. Положили драйвер БД — получили DataSource.
Встроенный Tomcat — приложение запускается как обычный jar через main, отдельный сервер приложений не нужен.
@SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan. Поэтому классы должны лежать в пакете главного класса или ниже — иначе Spring их не найдёт.
Spring Boot 3 требует Java 17+ и перешёл с javax на jakarta — учитывайте при импорте аннотаций валидации.

Spring построен на инверсии управления, а внедрение зависимостей — способ её реализации.
Что это означает на пальцах? Раньше вы писали набор классов, сами создавали объекты, связывали их и передавали из одного места в другое.
При работе со Spring у вас есть контейнер с бинами — объектами, жизненным циклом которых управляет Spring. Это контекст приложения.
Каждый бин объявляет свои зависимости — какие объекты ему нужны для работы. Spring сам создаёт их в нужном порядке и связывает между собой.

Теперь не вы управляете потоком выполнения — фреймворк вызывает ваш код. Это и есть IoC: «не звоните нам, мы сами вам позвоним».
Обратите внимание: вы не писали запуск и остановку сервера, в main почти ничего нет, а запрос сам доходит до метода контроллера.

Внедрение зависимостей — класс получает готовые объекты-зависимости снаружи, а не создаёт их сам. Способы: через конструктор, сеттер или поле. Рекомендуемый — через конструктор: поля можно сделать final, а в тестах легко передать заглушки. Если конструктор один, @Autowired не нужен.
Так мы получаем слабую связанность компонентов и простое тестирование.

REST

  • Representational state transfer
  • Архитектурный стиль
  • JSON — представление ресурса
  • Ресурсы адресуются через URL: /tasks, /tasks/{id}/subtasks, /tasks?priority=10
  • Часто называют любой HTTP API, хотя многие нарушают stateless или HATEOAS
Кто слышал про REST до хард-вебинара? Поставьте +.
Передача репрезентативного состояния. Впервые описан в диссертации Роя Филдинга в 2000 году.
Это архитектурный стиль взаимодействия физически разделённых компонентов, например клиента и сервера по сети.
Ограничения REST: клиент-сервер, stateless, кэшируемость, единообразный интерфейс, многоуровневая система и опционально код по запросу.

Согласно REST за каждым URL скрывается ресурс, действия с ним описываются методами HTTP. Клиент получает не сам ресурс, а его представление — JSON, XML или HTML-страницу.
Единого стандарта, что размещать в path, query params и body, нет.
Чаще всего ресурс — существительное во множественном числе, в path идентификаторы и вложенность, в query params фильтры и пагинация, в body данные. Методы HTTP — глаголы.

Из-за отсутствия строгих формулировок REST часто нарушают.
Stateless — сервер не хранит состояние сессии клиента, каждый запрос самодостаточен. Данные в БД это не нарушает.
HATEOAS — ответ должен содержать ссылки на возможные действия с ресурсом. На практике почти никогда не выполняется.
Есть модель зрелости Ричардсона: уровень 0 — всё через один URL и POST, 1 — ресурсы, 2 — методы HTTP и коды ответа, 3 — HATEOAS. Большинство API живёт на втором уровне, и этого достаточно.

Что такое безопасность и идемпотентность метода? Кто расскажет?
Безопасный метод не меняет состояние сервера: GET, HEAD, OPTIONS.
Идемпотентный — повторный вызов даёт тот же эффект, что и первый: безопасные плюс PUT и DELETE. POST не идемпотентен — два запроса создадут два фильма. PATCH в общем случае тоже.
Коды ответа: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 404 Not Found, 409 Conflict, 500 Internal Server Error. 4xx — виноват клиент, 5xx — сервер.
В ФП обновление сделано через PUT /films с id в теле, а не PUT /films/{id} — хороший пример «почти REST». Делайте так, как ожидают тесты.

Наследование

  • Делает классы сильно связанными
  • «Нарушает» инкапсуляцию
  • Усложняет изменения


Композиция

  • Слабо связывает классы
  • Реализацию можно заменить в рантайме
  • Упрощает тестирование
https://softwareengineering.stackexchange.com/a/371715
Хочу поговорить с вами про композицию. «Предпочитайте композицию наследованию» — совет ещё из книги банды четырёх 1994 года, и ему посвящён Item 18 в Effective Java Джошуа Блоха.
Композиция по-простому — это наличие объекта одного класса как поля в другом.
Если наследование — отношение «является», то композиция — «содержит».

Наследование делает классы сильно связанными: поведение потомка можно сломать, изменив родителя, тестировать их нужно вместе. Чтобы понять, как работает потомок, нужно разобраться в коде родителя.
Нарушает инкапсуляцию в том смысле, что потомок зависит от деталей реализации родителя — вот так один принцип ООП противоречит другому. :)
Классический пример из Блоха: наследник HashSet считает добавленные элементы, переопределив add и addAll. Но addAll внутри HashSet вызывает add, и каждый элемент считается дважды. Узнать это можно только из исходников родителя.
Затрудняет изменения: если вы привязали двух потомков к одному предку, а потом понадобилось изменить логику только одного из них, придётся их отвязывать.

При композиции вы сами регулируете, насколько связаны классы: делаете интерфейс с теми методами, которые нужны классу, и создаёте поле интерфейсного типа.
Зависимость — это поле, поэтому во время выполнения её можно заменить на другую реализацию. Иерархия наследования после компиляции неизменна.
С композицией просто тестировать: подставьте вместо зависимостей заглушки, сэмулируйте их работу и проверяйте класс в изоляции.
Именно на этом построен DI в Spring: сервис содержит поле с интерфейсом хранилища, а реализацию подставляет Spring. В следующем спринте вы так и сделаете.
Если хотите использовать наследование только чтобы переиспользовать код — скорее всего, лучше применить композицию.

В исходниках Java полно наследования — она писалась давно, с тех пор техники разработки поменялись, а центральные компоненты переписывать больно из-за обратной совместимости.
Пример — Stack наследуется от Vector. Так как Vector — конкретный класс, в стек попадает куча методов, противоречащих логике стека: доступ по индексу, вставка в середину, поиск. Та же история с Properties extends Hashtable. Вместо Stack документация рекомендует ArrayDeque.

ФП10 Filmorate начало

  • Валидация и логирование

В GitHub у вас должен появиться репозиторий java-filmorate, работаем в нём. Репозиторий должен быть публичным.

Как сдавать? От main создаёте ветку строго с названием controllers-films-users, делаете Pull Request в main. Запустятся автопроверки в GitHub Actions. Если зелёные — отправляете ссылку на PR на ревью.
Мержить сразу не надо. Если что-то правим — пушим в ту же ветку, PR обновится сам. Когда ревьюер дал добро — мержим.
Важно, что все проекты в курсе делаем на JDK 21. На это завязаны в том числе автопроверки.

Модели. Film: id, name, description, releaseDate, duration. User: id, email, login, name, birthday.
Даты — LocalDate, Jackson в Spring Boot сериализует его в формате yyyy-MM-dd. duration — целое число минут, не java.time.Duration, иначе не совпадёт с форматом в тестах.

Lombok. @Data = @Getter + @Setter + @ToString + @EqualsAndHashCode + @RequiredArgsConstructor. Lombok работает на этапе компиляции через annotation processor, в рантайме его нет — поэтому scope provided.
Для JDK 21 нужен Lombok 1.18.30 или новее. В IDEA плагин встроен, но нужно включить annotation processing.
@Slf4j генерирует поле private static final Logger log — ручной LoggerFactory.getLogger не нужен.
DELOMBOK показать — Refactor → Delombok в IDEA, видно, какой код на самом деле генерируется.
С кодогенерацией надо быть аккуратнее. Из последнего: вынес часть логики в отдельный пакет, а @Builder генерирует package-private конструктор, если других конструкторов нет. При подключении зависимости из другого пакета использовать его не смог — пришлось разбираться.
Кстати, Ломбок — остров в Индонезии недалеко от Явы, отсюда и название.

Хранение. Пока в памяти: Map<Long, Film> прямо в контроллере, id генерируем сами — счётчиком или max + 1, как в Catsgram. После перезапуска данные пропадут — нормально, БД будет позже.

Эндпоинты: POST /films, PUT /films, GET /films, и то же для /users. id при обновлении приходит в теле. POST и PUT возвращают созданную или изменённую сущность. Тело запроса — через @RequestBody.
При обновлении проверьте, что сущность с таким id существует, иначе ошибка, а не создание новой.

Валидация. Film: name не пустой; description не длиннее 200 символов; releaseDate не раньше 28 декабря 1895 — это день первого платного киносеанса братьев Люмьер; duration положительное.
User: email не пустой и содержит @; login не пустой и без пробелов; если name пустой — подставляем login; birthday не в будущем.
Граничные значения для тестов: ровно 200 символов — ок, 201 — ошибка; 28.12.1895 — ок, 27.12.1895 — ошибка; duration 0 — ошибка; день рождения сегодня — ок, завтра — ошибка. Проверьте null-поля и пустой запрос — NullPointerException не должен утекать.
Для ошибок валидации — своё ValidationException. Без обработки Spring вернёт на него 500. Какие коды ждут тесты, смотрите в Postman-коллекции. Нормальная обработка исключений будет в следующем спринте.
Валидацию удобно вынести в отдельный метод — тогда unit-тесты пишутся без поднятия Spring.

Логирование: логируем создание и обновление сущностей на INFO и причину ошибки валидации на WARN.

Postman-коллекцию импортируйте в Postman, запустите приложение и прогоните коллекцию целиком — это те же проверки, что и в автотестах.

Задача со звёздочкой — валидация аннотациями. Подключаете spring-boot-starter-validation, ставите @NotBlank, @Email, @Size(max = 200), @Positive, @PastOrPresent на поля модели, а в контроллере — @Valid рядом с @RequestBody. При ошибке Spring сам вернёт 400.
Импорт из jakarta.validation, а не javax. @Email пропускает null и пустую строку, поэтому нужен ещё @NotBlank. Логин без пробелов — @Pattern(regexp = "\\S+").
Стандартной аннотации для даты релиза нет. Для двух звёздочек напишите свою: аннотация с @Constraint, @Target, @Retention(RUNTIME) и класс-валидатор, реализующий ConstraintValidator. Это хорошо закрепит тему аннотаций.
