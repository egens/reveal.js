Single responsibility


				class Order {
					void createOrder() { /* ... */ }
				}

				class DiscountCalculator {
					void applyDiscount(Order order) { /* ... */ }
				}

				class OrderRepository {
					void saveToDatabase(Order order) { /* ... */ }
				}

				class NotificationService {
					void sendConfirmationEmail(Order order) { /* ... */ }
				}
Представьте, что вы проектируете класс Order в интернет-магазине. Какие задачи он может выполнять? Создавать заказ, Рассчитывать скидки, Сохранять заказ в базу, Отправлять email-подтверждение. Если всё это будет в одном классе, то: При изменении логики отправки email (например, добавить SMS) придётся менять Order. Если сломается расчёт скидок, может перестать работать и сохранение в БД. Тестировать такой класс сложно — слишком много зависимостей. SRP говорит: класс должен иметь только одну причину для изменения, то есть одну зону ответственности. Как исправить? Разделим Order на отдельные классы: Плюсы: Код проще тестировать (можно мокать NotificationService отдельно). Изменения в одной части системы не ломают другую. Код читаемее — каждый класс делает что-то одно. Ошибки: Дробить классы слишком сильно (например, создавать отдельный класс для форматирования даты в email). Путать SRP с «одним методом» (класс может иметь несколько методов, но они должны относиться к одной задаче). Итог: SRP — это про управляемость кода. Если класс делает слишком много — это повод для рефакторинга. Первый, самый известный и кажется, что самый понятный принцип — единственной ответственности.

Проще пойти от плохого — как не надо делать. Красный флаг, когда класс содержит в своем интерфейсе два публичных метода и по 500 строк приватных методов, часть из которых обеспечивает работу одного публичного метода, часть другого, а часть — оба.

Это сложно неудобно читать потому что много и изменять потому что методы могут влиять друг на друга.

На собеседованиях Часто говорят "класс должен делать что-то одно".

На самом деле в первоисточнике цитата немного другая — "класс должен иметь одну причину для изменения"

Попробуйте описать, что именно делает класс. Если не получается обойтись без союза "и", его нужно декомпозировать. Опять же, все зависит от контекста системы — например если класс шифрует и вычисляет хеш строки, но эти действия в системе не выполняются отдельно друг от друга, то это не нарушение. Есть набор признаков, по которым можно предположить нарушение SRP. Если класс очень большой, скорее всего он нарушает SRP. Большие классы, которые много чего делают называют классами Бога. Если при использовании класса тем или иным образом большАя часть методов не запускаются, то он возможно нарушает SRP.

Есть и обратные примеры — метод toString() присутствует у всех объектов в Java, но далеко не всегда используется. Это сделано для удобства, все об этом знают, поэтому это не вызывает проблем.

String — и многие другие классы стандартной библиотеки нарушают этот принцип, потому что являются классами Бога.

Подходит не только для классов, но и на других уровнях. В философии Unix есть аналог — Do One Thing And Do It Well. (программы должны делать что-то одно и делать это хорошо).

Open–closed


				class ReportGenerator {
					void generate(String format) {
						if (format.equals("PDF")) { /* ... */ }
						else if (format.equals("Excel")) { /* ... */ }
					}
				}
			

				interface Report {
					void generate();
				}

				class PdfReport implements Report { /* ... */ }
				class ExcelReport implements Report { /* ... */ }

				class ReportGenerator {
					void generate(Report report) {
						report.generate();
					}
				}
"Допустим, у вас есть класс ReportGenerator, который создаёт отчёты в формате PDF. Через месяц появляется требование добавить генерацию в Excel. Как это реализовать? Плохой подход: При добавлении нового формата (например, CSV) нужно лезть в ReportGenerator. Риск сломать существующую логику. Решение по OCP: Классы должны быть открыты для расширения, но закрыты для изменений. Создаём абстракцию: Плюсы: Новый формат? Просто добавляем CsvReport — старый код не трогаем. Удобно тестировать (можно подменить Report на заглушку). Где применять: Плагинные архитектуры (например, обработчики платежей). Алгоритмы, которые могут меняться (сортировка, фильтрация). Ошибки: Создавать абстракции «на будущее» (если система никогда не будет расширяться, OCP избыточен). Нарушать LSP (например, если ExcelReport выбросит исключение для некоторых данных). Итог: OCP снижает стоимость изменений. Продумывайте точки расширения заранее." Что значит? Что будет если не соблюсти? Как добиться?

Новая функциональность должна размещаться в новых классах. Старые классы должны изменяться только при баг фиксах.

Изменение — причина ошибок. Любое изменение, даже минимальная правка условия может внести ошибку — логическую, которую сложнее найти, или синтаксическую. Человек переоценивает свои силы, когда думает — сейчас вот тут поправлю метод и закину в прод, ничего не случится. Рано или поздно случится.

Поэтому так важны тесты и их запуск перед каждым пушем.

Liskov substitution


				class Bird {
					void fly() { /* ... */ }
				}

				class Penguin extends Bird {
					@Override
					void fly() {
						throw new UnsupportedOperationException("Пингвины не летают!");
					}
				}
			

				class Bird { /* ... */ }
				class FlyingBird extends Bird { void fly() { /* ... */ } }
				class Penguin extends Bird { /* ... */ }
			

				interface Flyable { void fly(); }
				class Sparrow implements Flyable { /* ... */ }
				class Penguin implements Swimable { /* ... */ }
У вас есть иерархия: класс Bird и подкласс Penguin. В Bird есть метод fly(). Что произойдёт, если Penguin попытается летать? Нарушение LSP: Проблема: клиентский код, работающий с Bird, сломается для Penguin. Как исправить? Пересмотреть иерархию: Использовать интерфейсы: Правило LSP: Подклассы должны дополнять, а не изменять поведение родителя. Пример из Java: ArrayList и LinkedList работают одинаково для методов List (хотя внутри реализация разная). Но если переопределить add() так, чтобы он удалял элементы — это нарушит LSP. Ошибки: Пустые методы в подклассах (@Override void fly() {}). Усиление предусловий (например, требовать speed > 100 в подклассе, если в родителе было speed > 0). Итог: LSP — это про предсказуемость. Наследование должно быть логичным, а не механическим. Принцип подстановки Барбары Лисков.

Часто отвечают, что при использовании в программе потомков вместо родителей не должна нарушаться логика приложения. Но это не совсем верно.

Метод может поддерживать работу с разными потомками, но при этом содержать условную конструкцию по типу аргумента.

Ее надо дополнять при добавлении нового типа. Такой метод нарушает принцип открытости/закрытости — его нужно изменять.

Поэтому важным в определении принципа является последняя фраза "использовать не зная об этом".

Для этого поведение потомков не должно противоречить поведению, заданному базовым классом.

То есть этот принцип больше про саму иерархию классов — ее надо разрабатывать так, чтобы в коде не нужно было разбираться с кем мы работаем — с родителем или потомком.

Не всегда логичные иерархии из окружающего мира хорошо ложатся в программные иерархии. Например, квадрат это прямоугольник. Но если отнаследовать квадрат от прямоугольника могут возникнуть проблемы — контракт прямоугольника предполагает методы по изменению длины и ширины независимо — если код программы будет использовать эту информацию, то он будет ломаться с квадратом.

В конкретном примере есть решение — например сделать объекты immutable. Но если это невозможно, то нужно менять иерархию — квадрат и прямоугольник к примеру должны наследоваться оn shape фигуры.

Для этого правила есть относительно строгие критерии, которым должен соответсвовать класс наследника, скину ссылку. https://www.baeldung.com/java-liskov-substitution-principle

Interface segregation


				interface Printer { void print(); }
				interface Scanner { void scan(); }
				interface Fax { void fax(); }
			

				class SimplePrinter implements Printer { /* ... */ }
				class OfficePrinter implements Printer, Scanner, Fax { /* ... */ }
"Представьте интерфейс MultiFunctionPrinter с методами: print(), scan(), fax(). Что делать, если у вас есть простой принтер без сканера? Придётся реализовывать scan() с пустым телом или исключением. Это нарушает ISP. Решение: Разделим интерфейс на части: Теперь классы реализуют только нужное: Плюсы: Нет «мусорных» методов. Клиенты зависят только от того, что используют. Пример из Java API: List — базовый интерфейс, RandomAccess — маркерный для быстрого доступа. Класс LinkedList не реализует RandomAccess, но это не ломает код. Ошибки: Дробить интерфейсы слишком сильно (например, создавать ColorPrinter и BlackWhitePrinter). Игнорировать ISP в DTO (интерфейсы для данных часто избыточны). Итог: ISP уменьшает связанность. Интерфейсы должны быть узкими и специализированными. Часто отвечают — много маленьких интерфейсов лучше чем один.

Еще один ответ — интерфейсы должны содержать логически обособленные, связанные между собой методы.

На самом деле этот принцип чуть глубже — в каноне Программные сущности не должны зависеть от методов, которые они не используют.

То есть это не про интерфейсы как часть языка программирования, а про взаимодействие объектов в целом (хотя это связано с интерфейсами).

Интерфейсы должны представлять дискретное обособленное поведение.

Этот принцип также иногда называют принципом единственной ответственности для интерфейсов.

Dependency inversion


				interface HttpClient {
					String get(String url);
				}

				class ApacheHttpClient implements HttpClient { /* ... */ }
				class MockHttpClient implements HttpClient { /* ... */ }
			

				class WeatherService {
					private final HttpClient client;

					WeatherService(HttpClient client) {
						this.client = client;
					}

					String getForecast() {
						return client.get("https://weather.com/api");
					}
				}
У вас есть класс WeatherService, который напрямую создаёт HttpClient для запросов к API. Проблемы: Тесты требуют реальных запросов (медленно и ненадёжно). Если нужно сменить библиотеку (например, с Apache на OkHttp), придётся переписывать WeatherService. Решение по DIP: Зависим от абстракций: Внедряем зависимость: Плюсы: Легко подменить реализацию (например, для тестов). Код устойчив к изменениям библиотек. Где применять: Работа с БД (DatabaseRepository → DataSource). Внешние сервисы (платёжные системы, API). Ошибки: Создавать абстракции для всего подряд (например, для DTO). Игнорировать DI-контейнеры (вручную передавать зависимости сложно в больших проектах). Итог: DIP делает код гибким. Зависите от интерфейсов, а не от конкретных классов." SOLID — это не догма, а инструмент. Начинайте с малого: сначала SRP и DIP, потом остальное. Со временем вы научитесь чувствовать, когда принцип уместен, а когда — избыточен. Проверить понятно ли тут написано? Модули верхнего Уровня не должны зависеть от модулей нижнего уровня. И те и другие должны зависеть от абстракций (интерфейсов).

И вторая часть — абстракции не должны зависеть от деталей. Детали (конкретные имплементации) должны зависеть от абстракций.

Где тут инверсия — традиционно модули верхнего уровня зависят от нижнего, с DI наоборот — модули нижнего уровня зависят от интерфейсов модулей верхнего уровня.

Этот принцип помогает обеспечить низкую связность программных модулей между собой.

Я уже говорил, что хорошее приложение это не столько про работающий код в классах, сколько про то, как они взаимодействуют между собой.

Тут можно вспомнить концепцию высокой сцепленности внутри программного модуля, и низкой связности взаимодействия между модулями.

Разработка через интерфейсы и использование инверсии зависимостей ведет к тому, что разработчик больше задумывается об интерфейсах и о взаимодействии классов между собой, что положительно сказывается на архитектуре приложения.

Применение этого принципа облегчает тестирование, хотя современные методы тестирования позволяют использовать болванки и вместо конкретных классов.
