112. Path Sum 

						class Solution {
							public boolean hasPathSum(TreeNode root, int targetSum) {
								if (root == null) {
									return false;
								}

								if (root.left == null && root.right == null) {
									return targetSum == root.val;
								}

								boolean leftSum = hasPathSum(root.left, targetSum - root.val);
								boolean rightSum = hasPathSum(root.right, targetSum - root.val);

								return leftSum || rightSum;
							}
						}


https://leetcode.com/problems/delete-characters-to-make-fancy-string/description/ 

						class Solution {
							public String makeFancyString(String s) {
								char prev = s.charAt (0);
								int freq = 1;
								StringBuilder res = new StringBuilder ();
								res.append (s.charAt (0));
								for (int i = 1; i < s.length (); i++) {
									if (s.charAt (i) == prev)
										freq++;
									else {
										prev = s.charAt (i);
										freq = 1;
									}
									if (freq < 3)
										res.append (s.charAt (i));
								}
								return res.toString ();
							}
						}

						public class Solution {
							public ListNode getIntersectionNode(ListNode headA, ListNode headB) {
								ListNode a = headA;
								ListNode b = headB;

								while( a != b){
									a = a == null? headB : a.next;
									b = b == null? headA : b.next;
								}

							}

MongoDB

— Напишите с какими БД может быть кто-то работал вне курса или минус если не работали.

MongoDB популярная NoSQL БД.

Данные вместо строк хранятся в JSON подобной структуре. Таблицам соответствуют коллекции.

Зачем это надо?

В SQL можно хранить сложные структуры, нужно велосипедить сложные схемы БД с набором таблиц. В MongoDB можно просто вставить ассоциативный массив.

Чтобы из SQL восстановить сложные объекты с вложенностью и полями-списками, нужны JOIN. Но часто при работе с объектами они всегда нужен целиком, то есть JOIN будет постоянно выполняться, это лишняя нагрузка. MongoDB решает эту проблему.

У документов динамическая схема, то есть набор полей может меняться внутри одной коллекции — это полиморфизм на уровне БД.

Запросы пишутся на собственном скриптовом языке, есть плагины для многих ЯП.

Одна из центральных фич — горизонтальное масштабирование, шардинг. Поддерживаются индексы, сложные запросы, агрегации, материализованные вьюхи.

Вообще несмотря на очень разное устройство разных БД, важно понимать, что они универсальны и функционально очень похожи. Просто некоторые вещи удобнее делать на разных БД. Одно из важных умений инженера — понять, какую лучше применить. Для этого надо иметь разнообразный опыт работы.

Elasticsearch/Opensearch

inverted full-text index
Elasticsearch как и MongoDB документное хранилище, его фишка — в обратных полнотекстовых индексах для записываемых данных. Также хранилище позиционируется как аналитическое.

Что такое inverted full-text index? Когда текстовый документ сохраняется, он разбивается на слова и они добавляются в обратный индекс — по сути как содержание в книге.

Для каждого слова есть список ссылок на документы, в которых он содержится.

Эта БД также из коробки распределенная и горизонтально масштабируемая.

В основе лежит технология Apache Lucene — движок полнотекстовой индексации и поиска.

Эта БД используется для поисковых движков на сайтах и для хранения и анализа логов в связке ELK — Elasticsearch Logstash Kibana

Сейчас в РФ переходят на стэк от OpenSearch.

Redis

remote dictionary server
Redis — резидентная СУБД, то есть размещаемая в оперативной памяти и из-за этого очень быстрая.

Его позиционируют как кэш и брокер сообщений. С возможностью распределенного хранения.

Но чаще он по-моему используется как быстрое key value хранилище, вы уже видели такое в предыдущих спринтах.

СУБД оперирует данными в памяти, но при каждом изменении, данные сохраняются на диск, то есть не теряются при перезапуске БД.

На картинке представлен один из вариантов использования Redis в качестве кэша перед обычной БД.

В ключ записываются параметры запроса и при получении такого же, данные вытаскиваются из значения Redis вместо БД.  Конечно, есть механизмы управления сроком жизни кеша, потому что данные в БД меняются и результат запроса тоже.

Я вам показал только 3 примера популярных хранилок. Но их на самом деле десятки, изучением особенностей работы с ними можно заниматься бесконечно.

Реляционные базы данных основаны на теории отношений (relation), хотя в теории написано, что это связь. Чтобы вас не грузить, но я решил, что будет полезно.

Это прикладная область математики, в которой таблицы называются отношениями, а строки кортежами — такие названия вы тоже можете услышать, но редко.

Разные SQL БД имеют разный синтаксис в мелочах — с этим многие уже успели столкнуться.

Кто смотрел видео про нормальные формы? + / - А кто что-то понял из видео?

Нормализация это декомпозиция таблиц с целью устранения аномалий.

Пример аномалии — столбец с жанром фильма, если нужно будет менять название какого-то жанра, то это надо будет сделать во всех строчках, где он используется — можно вынести такой атрибут в отдельную таблицу.

Как сказано в видео — максимальная нормализация вредна, потому что БД начинает тормозить, поэтому обычно этот процесс ограничивают. А вообще для больших и сложных приложений проектированием БД занимают отдельные люди — Database administrator. Это точно не должен делать разработчик, у меня есть плохие примеры из практики. На собеседованиях могут спрашивать про JOIN и HAVING, хотя HAVING я вообще по-моему не использовал в работе.
