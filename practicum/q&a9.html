В этом спринте вам рассказали на пальцах как устроен интернет. Это компьютерная сеть планетарного масштаба.

Взаимодействие в этой сети описывается спецификацией, которая иногда называется TCP/IP — по самым популярным протоколам транспортного и сетевого уровня, которые в ней используются.

Взаимодействие происходит на разных уровнях, по ним обычно гоняют сетевых инженеров, но могут задать вопрос и на собеседовании разработчика, если понимание модели сети важно для работы.

Вы разобрали в браузере на примерах, как работает клиент-серверное взаимодействие по протоколу HTTP на примере использования разных методов.

Напишите, какие методы HTTP вы знаете? GET POST PUT PATCH DELETE HEAD CONNECT OPTIONS TRACE

Для обеспечения работы пользовательских сервисов в интернете — магазинов, соцсетей, поисковых движков, — разработчики пишут WEB API.

API присутствуют у любого достаточно популярного сервиса и их полезно поизучать, чтобы на примерах посмотреть, какие принципы применяются при написании.

Распространенным форматов обмена данными является JSON, давайте проверим, как вы поняли этот формат.

Массив, объект, строка, число, булево, нуль.
  • {1}
  • {2: 2}
  • {"3": 3}
  • {"4": [4]}
  • [5, "5"]

JSON состоит из значений различных типов.

object, array — составные типы, это ассоциативный массив (строка: json) и список json.

Парcеры JSON могут иметь нюансы на граничных случаях — может ли быть массив на верхнем уровне.

Зачем читать RFC?

  • HTTP 7231 — Раздел 4.2
  • Безопасные методы
    GET, HEAD, OPTIONS, TRACE
  • Идемпотентные методы
    PUT, DELETE + безопасные
  • POST, PATCH — небезопасные и неидемпотентные
В лекциях дана ссылка на HTTP RFC, поставьте + кто его открывал? Там 100 страниц.

Знакомиться с документацией — важно, потому что в ней могут быть описаны нюансы работы. Например раздел 4.2 разделяет методы HTTP на безопасные, идемпотентные и обычные.

Безопасные методы осуществляют по сути операции чтения и не должны иметь побочных эффектов на сервере. При проектировании API не нужно ставить на метод GET изменение какого-либо состояния или нагруженные операции.

Идемпотентные методы — когда результат работы сервера не зависит от количества идентичных запросов — будь то 1 или несколько. РАСХОЖДЕНИЕ С ХАРД ВЕБИНАРОМ.

Прокси, Кеши, веб краулеры могут повторять и выполнять безопасные методы. И повторять идемпотентные методы, если случилась ошибка. Но не будут этого делать с другими методами.

Конечно вряд ли на ваш сервис будет ходить краулер гугла.

Но вы точно можете столкнуться с особенностями работы клиента-браузера.

СКИНУТЬ ССЫЛКУ

REST

  • Representational state transfer
  • Архитектурный стиль
  • Веб-страница — представление ресурса
  • Ресурсы скрыты за url
    /tasks
    /tasks/{id}/subtasks
    /tasks?priority=10
  • Часто называют любой HTTP API
    Хотя они нарушают Stateless или HATEOAS
Что такое REST кто слышал до хард вебинара + ?

Передача репрезентативного состояния. Первое упоминание в диссертации Роя Филдинга в 2000г.

Архитектурный стиль описывающий взаимодействие физически разделенных компонент, например по сети интернет в клиент-серверной архитектуре.

Согласно REST за каждым url web api скрывается ресурс, действия с которым описываются различными методами HTTP. А веб-страница является пользовательским представлением ресурса или нескольких ресурсов.

Ресурсы скрыты за URL, нет единого подхода к формированию — что размещать в path, query params и body запроса.

Но чаще я встречал, что ресурс — существительное во множественном числе, в path содержатся идентификаторы элементов, поддерживается вложенность ресурсов, в query params добавляются фильтры ресурса, а в body передаются данные. Методы HTTP — глаголы, описывающие действия над ресурсом.

Из-за отсутствия строгих формулировок часто нарушается в некоторых моментах. Например stateless, то есть сервер не должен использовать информацию от предыдущих запросов пользователя.

HATEOAS — ответ ресурса должен содержать гиперссылки на возможные действия с этим ресурсом. Это практически никогда не выполняется.

SOAP

  • Simple Object Access Protocol
  • Протокол обмена сообщениями
  • Формат данных XML
  • Ни черта не Simple
SOAP старше REST на пару лет и более строго описывает взаимодействие. Разработан в 1998 году.

Это простой протокол обмена сообщениями на основе формата XML.

Для передачи используется один из протоколов прикладного уровня, то есть в отличие от REST не привязан к транспортному протоколу. HTTP, MQP, UDP

Не простой, основан на многословном формате XML, который сложно генерировать и парсить. Поэтому чаще используют JSON HTTP API.

ФП9 Трекер задач API

  • 🎬 MovieHub — REST API для кинотеатра: тестируем через TDD, а не «пишем и молимся»
  • 🔴🟢🔵 Red-Green-Refactor: сначала падающий тест, потом минимальный код, потом чистим
  • 🧱 Архитектура: MoviesServer → BaseHttpHandler → MoviesHandler, плюс Movie, MoviesStore, ErrorResponse
  • 🛠 Стек: HttpServer/HttpClient из JDK, JUnit 5 (@BeforeAll/@AfterAll), Gson для JSON
Сегодня разберём проект MovieHub — маленький REST-сервис со списком фильмов, который вы будете собирать через TDD. Это первый раз в курсе, когда вы пишете тест раньше, чем код, и я хочу, чтобы вы понимали не просто «что копировать», а зачем вообще так делать.

Смотрите, весь процесс строится вокруг трёх этапов, которые в TDD называют красный-зелёный-синий. На красном этапе вы пишете тест, который проверяет требование из спецификации — например, что GET-запрос на /movies при пустом хранилище должен вернуть 200 и пустой массив. Тест этот, естественно, падает — сервера-то ещё нет. И это нормально, это не баг, это ожидаемое состояние, отсюда и название «красный».

На зелёном этапе ваша задача — написать минимальный код, чтобы тест начал проходить. Не идеальный, не продуманный на все случаи жизни — именно минимальный. Здесь вы поднимаете HttpServer, вешаете хендлер на /movies, и хендлер просто отдаёт захардкоженный пустой массив. Звучит как читерство, но это ключевая идея TDD: не пишите код, который не требуется тестом прямо сейчас.

А дальше — синий этап, рефакторинг. Вот тут начинается самое интересное и самое важное для вас как будущих разработчиков. Вы смотрите на код и ищете дублирование. Заметили, что отправка JSON-ответа — это всегда одни и те же три действия: заголовок Content-Type, преобразование в байты, запись в поток? Значит, выносим это в BaseHttpHandler с методами sendJson и sendNoContent, а MoviesHandler просто наследуется от него. То же самое с тестом: запуск сервера и создание клиента — это подготовка, которая повторится для каждого теста, значит выносим в @BeforeAll, а не копируем в каждый метод.

И вот тут я хочу, чтобы вы поняли главное: рефакторинг безопасен именно потому, что у вас есть тесты. Вы можете смело переписывать структуру кода, и если что-то сломается — тест сразу покраснеет и вы это увидите. Без тестов такой уверенности нет, вы просто гадаете, не сломали ли что-то в другом месте.

По архитектуре — не пугайтесь количества классов. Movie — это просто модель данных фильма. MoviesStore — хранилище, где происходит добавление, поиск, удаление. ErrorResponse — единый формат для ошибок, чтобы клиент API всегда получал предсказуемую структуру, а не разнобой из строк и кодов. Это ровно то разделение ответственности, которое от вас будут ждать и в реальных проектах: хендлер не должен знать, как устроено хранилище, а хранилище не должно знать про HTTP.

Отдельно скажу про порядок тестов. Если сервер запускается один раз на весь класс тестов через @BeforeAll, то состояние между тестами не сбрасывается само. Значит, либо вы жёстко упорядочиваете тесты аннотациями, что делает их зависимыми друг от друга и вообще не лучшая практика, либо добавляете метод очистки хранилища и вызываете его в @BeforeEach. Второй вариант почти всегда правильнее — тесты должны быть независимыми друг от друга.

И последнее: не забывайте проверять API руками через Insomnia или Postman, параллельно с автотестами. Автотесты покажут, что логика работает по спецификации, а ручная проверка — что вы вообще правильно понимаете, что возвращает сервер, и часто ловит опечатки в JSON или заголовках, которые тест мог пропустить.

Если по ходу работы застрянете на каком-то из этапов — красном, зелёном или синем — пишите в чат сразу, не держите вопрос при себе до дедлайна. У этого задания много мелких развилок, и лучше свериться на середине, чем переделывать всё в конце.
